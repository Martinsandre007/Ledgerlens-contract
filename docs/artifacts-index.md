# Machine-Readable Artifacts Index

This page is the single source of truth for every machine-readable artifact this project generates and publishes. Each entry describes the artifact's **purpose**, **format**, **location**, and **generating tool**, and carries a **freshness badge** that is updated automatically by the documentation site's build (and a scheduled job) so this index cannot silently go stale.

> **Freshness badges** are produced by `tools/docs-site/check-artifacts-freshness.mjs`. A badge reads `fresh` when the artifact in its published location matches what regenerating it from current source would produce, and `stale` when it has drifted. The check also fails the build if a generated artifact exists in the repository but is **not** listed on this page, so newly added artifacts cannot slip through unnoticed.

## How the inventory is derived

The list below is derived directly from the generating tools and workflows, not from memory. The authoritative inventory lives in `tools/docs-site/artifacts-inventory.json`, which is assembled from:

- `tools/schema-gen` — event schema, interface metadata, and related JSON Schema outputs.
- `tools/docs-site` — documentation site inputs and the freshness checker itself.
- `.github/workflows/*` — every workflow that runs a generator and publishes an artifact.
- `docs/risk-score-schema-generation.md` — the RiskScore schema generation pipeline and its derived bindings.

When a generator or workflow is added or changed, update `tools/docs-site/artifacts-inventory.json`; the freshness check will fail until the corresponding entry is added here.

## Artifacts

### Event schema

- **Purpose:** Canonical JSON Schema describing every emitted contract event, used by indexers, SDKs, and downstream consumers to decode and validate events.
- **Format:** JSON Schema (Draft 2020-12).
- **Location:** `schema/events/` (published with each release).
- **Generating tool:** `tools/schema-gen`.
- **Freshness:** _see badge above_

### Interface metadata

- **Purpose:** Machine-readable description of the contract's public interface (functions, arguments, return types, errors) for client generation and tooling.
- **Format:** JSON.
- **Location:** `schema/interface/`.
- **Generating tool:** `tools/schema-gen`.
- **Freshness:** _see badge above_

### SDK conformance fixtures

- **Purpose:** Golden fixtures that SDK implementations must pass to be considered conformant with the contract's behavior.
- **Format:** JSON fixtures.
- **Location:** `sdk/conformance/fixtures/`.
- **Generating tool:** `tools/schema-gen` (fixtures) driven by the conformance workflow.
- **Freshness:** _see badge above_

### Generated clients

- **Purpose:** Language-specific client bindings generated from the interface metadata so integrators do not hand-write contract calls.
- **Format:** Source code (TypeScript, and other supported languages).
- **Location:** `clients/` (per-language subdirectories).
- **Generating tool:** client generator invoked from the interface metadata pipeline.
- **Freshness:** _see badge above_

### Compliance report format

- **Purpose:** Machine-readable schema for compliance reports emitted by the compliance tooling, so reports can be validated and consumed programmatically.
- **Format:** JSON Schema.
- **Location:** `schema/compliance/`.
- **Generating tool:** compliance tooling schema generator.
- **Freshness:** _see badge above_

### Dependency graph

- **Purpose:** Machine-readable graph of crate/module dependencies used for supply-chain review and impact analysis.
- **Format:** JSON (graph of nodes and edges).
- **Location:** `artifacts/dependency-graph.json`.
- **Generating tool:** dependency graph workflow.
- **Freshness:** _see badge above_

### RiskScore schema

## Maintaining this page

1. Add or change a generator or workflow.
2. Update `tools/docs-site/artifacts-inventory.json` with the new artifact's id, purpose, format, location, and generating tool.
3. Add a matching entry to the **Artifacts** section above.
4. Run `node tools/docs-site/check-artifacts-freshness.mjs` locally; the build will regenerate the freshness block and fail if any artifact is missing from this page or has drifted from its source.

The freshness check runs as part of the documentation site build and on a scheduled job, so a forgotten artifact or a drifted artifact is caught automatically.
